# ADR-0010: One file per decision; the decision-log table is frozen

**Status:** Accepted
**Date:** 2026-09-17
**Issue:** #808
**Deciders:** developer (decision), agent (analysis and implementation)

## Context

`specs/decisions/DECISION-LOG.md` was a single Markdown table to which every PR carrying a
decision appended one row. Two appends to one file always conflict in git. When the
autonomous pipeline (#744) began producing PRs, #749 and #750 conflicted #751 on this file
the day before the dispatcher existed, and #744 had predicted exactly that.

The response in #753 was to serialise agent runs — `concurrency: agent-run`, one at a time
repository-wide. That stopped the conflicts and, while the dispatcher could not run at all,
cost nothing. Once it worked, the serialisation became the pipeline's bottleneck and the
source of three further defects:

- three issues labelled together took ~40 minutes in sequence, not ~15 in parallel;
- the one-deep shared queue cancelled every third label (#788);
- each run finishing after the previous merge left its PR BEHIND (#793).

The developer asked why development was sequential. The answer was that a documentation
convention was dictating the execution model.

## Decision

Each decision is its own file: `specs/decisions/log/YYYY-MM-DD-<slug>.md`, with
frontmatter `date`, `title`, `issue`, `category` and the reasoning as the body. New files
merge without conflict. The table is frozen at 135 rows with a header note; nothing appends
to it again.

There is **no committed index**. `script/decision-log.mjs` renders one on demand and
`--check` validates every entry; a Vitest test runs the check in CI. The directory is the
index.

`CLAUDE.md`, `DOC-AGENT-SPEC.md` (rule C-003), `AGENT-AUTONOMY-POLICY.md`, the pipeline
doc and the Doc Agent prompt are updated in the same PR. The concurrency change itself —
per-issue groups and a max-concurrent bound in `agent-dispatch.yml` — follows in a
separate gated PR, after this one is on `main`: agents must write to the new location
before they run in parallel.

## Alternatives considered

- **Keep the table, keep serialising.** Rejected: the cost is now measured in human waiting
  time and dropped labels, and it will grow with every issue the pipeline takes on.
- **Generated `INDEX.md` committed in each PR.** Rejected: it is regenerated by every PR and
  conflicts exactly as the table did.
- **Generated index committed to `main` by a workflow on push.** Rejected: a bot pushing to
  `main` needs to bypass branch protection, which is the one thing the protection exists to
  prevent.
- **Per-PR sections in the single file (one heading per PR).** Rejected: still one file;
  concurrent insertions at the end still conflict.

## Consequences

- Several agent PRs can merge in the same window with no manual rebase for the log.
- Reading history is now `ls specs/decisions/log/` plus the frozen table, or the script.
- The pipeline row "conflict on `DECISION-LOG.md` → rebase and retry" is retired.
  `package-lock.json` keeps its row.
- Every rule that said "add a row" now says "add a file"; a PR that adds a row to the
  frozen table fails the Doc Agent's C-003.

## Reversal

Restore appends to the table and `concurrency: agent-run`. Two files. The per-decision
files remain valid history either way.
